x402 proves a payment. Paxiom proves what the payment bought.

Paxiom binds payment, request, JSON or binary payload digest, seller key identity, and settlement metadata into an Ed25519-signed Payment-Receipt header that agents and developers can verify offline — or counter-attest against live Base USDC settlement for free.

Why this exists

A payment response is not proof of delivery.

x402 makes paid HTTP resources effortless: an agent pays, the server answers. But a payment succeeding is not evidence of what was delivered. A buyer wallet, audit log, or downstream machine still needs to verify:

  • what resource was paid for, and what exact request was bound to that payment;
  • whether the JSON or binary bytes delivered match the signed jcs-sha256 or raw-sha256 output commitment;
  • whether the signing key is authorized for the seller's HTTPS origin (/.well-known/x402-keys.json) and payTo recipient;
  • whether on-chain settlement was independently verified or merely claimed by the seller.

Instead of every x402 seller inventing an incompatible HMAC or signature header, paxiom.receipt.v0 defines one vendor-neutral Payment-Receipt format (with X-Paxiom-Receipt backward compatibility) and zero-dependency MIT tooling.

Claim boundary

Schema-valid is never called receipt-verified. In offline mode, a receipt carrying an unverified transactionHash resolves to settlement_claimed_not_checked — never verified. Only independent on-chain log verification via POST /v1/receipt/verify-live (counter-signed by a pinned verifier key in /.well-known/x402-keys.json) upgrades settlement to verified_settled.

The verdict

One deterministic trust state.

Every verification call returns one unambiguous trust state alongside per-check diagnostics:

verified valid_signature_only settlement_claimed_not_checked unauthorized_issuer output_hash_mismatch settlement_failed invalid_signature unsupported_format expired

All sixteen trust states and their strict precedence order are documented in the specification. Read the trust states →

Try it now

Install from npm/PyPI or verify over HTTP.

The reference SDKs, CLI, and MCP server ship with zero required dependencies on npm (@paxiom/receipts@0.2.0, Node ≥18) and PyPI (paxiom-receipts==0.2.0, Python ≥3.10):

# Install in an x402 seller or buyer project:
npm install @paxiom/receipts

# Generate an Ed25519 seller keypair via CLI:
npx --yes --package=@paxiom/receipts paxiom-receipt keygen --out ./seller-key-01.pem --key-id seller-key-01

# Run the stdio MCP server (verify_receipt, explain_receipt, issue_receipt, preflight_x402_seller):
npx --yes --package=@paxiom/receipts paxiom-receipt-mcp

# Or install the zero-dependency Python 3.10+ / FastAPI SDK from PyPI:
pip install paxiom-receipts

Query the free public reference verifier at https://api.paxiom.org:

curl -s https://api.paxiom.org/version
curl -s https://api.paxiom.org/v1/receipt/demo
curl -s https://api.paxiom.org/.well-known/x402-keys.json
Public reference runtime

https://api.paxiom.org serves free offline verification (POST /v1/receipt/verify), pre-payment seller scanning (POST /v1/x402/preflight), and live Base Mainnet settlement verification + counter-attestation (POST /v1/receipt/verify-live). Published verifier keys live at /.well-known/x402-keys.json (and /.well-known/paxiom-keys.json).
