Paxiom · Standard Specification Sheet
Trust States & Precedence
All fifteen verification verdicts and deterministic evaluation order.
Sheet PXM-RC-101· paxiom.receipt.v0· v0.1.3

Fifteen deterministic verdicts. Strict top-to-bottom precedence.

A conforming paxiom.receipt.v0 verifier consumes a receipt (and, where supplied, the delivered output) and emits exactly one trust state plus a structured per-check breakdown. Trust states are the honesty contract: they separate what was independently verified from what was merely claimed.

01 · The Enum

All fifteen trust states.

Trust stateMeaning
verifiedEverything the offline verifier can check passed, and settlement is either Paxiom-counter-attested or not an unconfirmed on-chain claim.
valid_signature_onlySignature is valid, but the verifier could not reach verified for a non-fatal reason (e.g., delivered output was not supplied, or settlement.status = unknown).

request_binding_missingRequired request binding fields absent or malformed.
payment_binding_missingRequired payment binding fields absent or malformed.
output_hash_mismatchSupplied output's canonical SHA-256 hash does not equal delivery.outputHash.
settlement_claimed_not_checkedSignature and output hash verified, but the receipt asserts an on-chain settlement that this verifier did not independently confirm.
settlement_failedsettlement.status = failed.
proof_not_providedEvidence array is empty or all not_provided (informational in check breakdown; does not by itself block verified).
proof_unavailableAn evidence record references an external artifact the verifier could not retrieve.
proof_invalidAn evidence record was retrieved and failed verification.
expiredexpiresAt is present and in the past relative to verifier evaluation time.
errorThe verifier itself encountered an unexpected failure (e.g., nesting depth > 256 or I/O error).
02 · Precedence

Resolution order (offline verifier).

Evaluate top-to-bottom and return the first rule that applies. This guarantees, for example, that a tampered payload always surfaces as output_hash_mismatch rather than silently degrading:

  1. Verifier exception → error.
  2. receiptVersion unrecognized → unsupported_format.
  3. Schema invalid → schema_invalid.
  4. Ed25519 signature fails over canonicalize({ receiptVersion, payload }) → invalid_signature.
  5. expiresAt present and past → expired.
  6. request bindings missing or malformed → request_binding_missing.
  7. payment bindings missing or malformed → payment_binding_missing.
  8. Output supplied and its canonical hash ≠ delivery.outputHash → output_hash_mismatch.
  9. settlement.status = failed → settlement_failed.
  10. Evidence retrieved and invalid → proof_invalid; referenced but unreachable → proof_unavailable.
  11. settlement.status ∈ { claimed_not_checked, verified_settled } without a trusted Paxiom counter-attestation key → settlement_claimed_not_checked (issuer self-assertions never self-promote to verified settlement).
  12. Output not supplied, or settlement.status = unknown → valid_signature_only.
  13. Otherwise → verified.
Counter-Attestation Upgrade

Calling POST https://api.paxiom.org/v1/receipt/verify-live verifies canonical Base USDC Transfer event logs directly on-chain and returns a Paxiom counter-signed receipt verifiable offline when Paxiom's published key (/.well-known/paxiom-keys.json) is passed in trustedPaxiomPublicKeys.
