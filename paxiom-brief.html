Paxiom Brief

Verified facts for autonomous agents.

Paxiom packages public-chain claims as paid, machine-callable attestations whose inputs can be checked, whose computation can be replayed, and whose evidence trail is permanent.

Public draft / 2026.05.10 / paxiom.org

In one sentence: Paxiom is an x402-payable, MCP-callable verification layer for agents, tools, and services that need answers they can verify later rather than claims they must trust now.

The shift in framing: Paxiom is not trying to replace every RPC, archive node, or data source. It is trying to remove blind trust from the answer. Data sources can be useful; unverifiable claims are not.

01 / Problem

Agents can pay for answers faster than they can trust them.

Agent infrastructure is moving toward machine-callable tools, automatic payments, and cross-service workflows. x402 gives agents a way to pay for an API call. MCP gives agents a way to discover and invoke tools. But neither protocol proves that a returned answer was correct.

That gap matters when the answer drives money movement, access control, cross-chain execution, compliance reporting, or private opportunity routing. A service can return a signed response, but a signature only proves who said it. It does not prove the claim itself.

Paxiom's core question is: when an agent receives a paid answer, can another party later verify why that answer was accepted?

02 / Product

Paxiom sells verifiable claims, not generic compute.

The Phase 1 product surface is a set of small, paid attestations: storage-slot proofs, sync-committee verification, cross-chain message verification, simulations, and verified historical-state queries. The buyer is not only a human developer. The buyer can be an agent, MCP tool, bridge monitor, compliance workflow, or private routing system.

The product is not "we know the answer." The product is "here is the answer, the proof packet, and the evidence needed to replay it."

Paxiom can also support private cross-chain opportunity feeds. AO messaging can coordinate observation and settlement across chains. That becomes an x402/MCP product only when packaged as something an agent can buy: a route, a simulation, a feed item, or an attestation.

03 / Architecture

The source can be useful without becoming trusted.

For Ethereum L1 historical state, Paxiom is moving toward a sovereign witness path first. Erigon or Reth can retrieve eth_getProof witnesses from infrastructure Paxiom controls. The current rehearsal path is a local Erigon archive syncing into a Google Drive-backed cold warehouse, with a local hot tier for active work. Any RPC-like path is treated as transport or convenience, not authority; the answer is checked against Ethereum state roots anchored by sync-committee verification.

The cold path is about auditability and replay. Paxiom's working direction is encrypted proof material on Arweave, Paxiom-controlled indexes and keys, and AO/HyperBEAM-assisted verification where data exposure is acceptable. Ultraviolet remains useful reference work, but Paxiom is no longer waiting on it to close the historical-state gate.

Transport Path

RPC-like sources can still move data, but they do not decide truth. Paxiom verifies witnesses against Ethereum roots before signing a response.

Sovereign Path

Erigon/Reth returns MPT witnesses from infrastructure Paxiom controls. Paxiom verifies the witness against a sync-committee-trusted Ethereum state root.

Cold Path

Encrypted Arweave storage preserves evidence and proof packets. AO/HyperBEAM make verification replayable where the data can safely be revealed.

04 / Difference

Paxiom is not trying to out-Lagrange Lagrange.

Lagrange, Axiom, Herodotus, Succinct, RISC Zero, and related systems are serious proof infrastructure. Some are better positioned for large coprocessor workloads, SQL-style proofs over on-chain data, universal proving, or direct protocol integrations.

Paxiom's lane is narrower and more agent-native: package verified public-chain facts as paid tool responses. The differentiator is not inventing MPT verification or running the biggest prover network. The differentiator is the combined product surface: x402 payment, MCP discovery, verified inputs, replayable execution, permanent evidence, and service-level packaging.

Competitors can add payment endpoints. Retrofitting replayable evidence as a native property is harder.

05 / Moat

The moat is the composition.

Verifiable Inputs

Witnesses are checked cryptographically instead of trusted because a provider returned them.

Agent-Native Sales

x402 makes each attestation payable by software. MCP makes the service discoverable and callable by agent frameworks.

Permanent Evidence

Encrypted Arweave bundles preserve proof packets and supporting evidence beyond Paxiom's own database while keeping the useful index and keys inside Paxiom.

Replayable Verification

AO/HyperBEAM gives the audit trail an execution surface, not just a storage location.

06 / Immediate Build Target

A-202 first, then local historical-state rehearsal.

The immediate revenue target is A-202: a sync-committee verification endpoint that is x402-payable, MCP-discoverable, signed by Paxiom's Ed25519 platform key, and packaged with replayable evidence fields. It is intentionally narrow because the goal is to prove the paid attestation loop while the local Erigon proof warehouse catches up for A-201 and A-205. The current hardening work rejects slot-mismatched device responses and keeps disabled/stub payment states from being described as settled.

  • Publish the deployed /.well-known/paxiom-platform-pubkey.json.
  • Deploy the Base Sepolia endpoint with REQUIRE_X402=1 and a real receiving wallet.
  • Confirm unpaid 402, paid 200, PAYMENT-RESPONSE, and X-PAXIOM-SIGNATURE together.
  • Verify the response signature locally from the published public key.
  • Only then run the MCP end-to-end rehearsal and compute mainnet unit economics.
07 / Position

The concise thesis.

Paxiom is infrastructure for autonomous economic activity that needs accountable answers. It does not depend on purity about data transport. It depends on proof: the answer must be independently checkable, replayable, and durable.

Data sources can be useful. Claims must be verifiable.
